### 1.4 现状系统概述

EDS 是一个基于 **Google Apps Script + Google Sheets** 的 Web 应用，以 Google Sheets 作为数据库。其技术特征会直接影响业务行为，Nexus 团队需了解：

- **单页多路由**：通过 URL 参数 `?v=页面名` 路由到不同页面
- **身份传递**：用户登录后信息存于浏览器 `sessionStorage`，页面间通过 URL 参数传递
- **后端即表格**：所有数据读写直接操作 Google Sheets 单元格
- **执行限制**：单次后端调用有 6 分钟上限；表格读取返回的日期是对象而非字符串

> **对 Nexus 的含义**：EDS 的诸多「业务规则」实际上是被表格特性倒逼出来的权宜之计（如靠字符串包含判断状态、靠列位置而非字段名定位数据）。Nexus 重建时应以本文档描述的业务意图为准，**不必复刻这些实现细节**——相关清单见附录 B。

## 2. 业务背景与目标

### 2.1 业务语境

设备部下设两条维护主线，构成 TPM（全员生产维护）的核心：

- **点检（日常自主维护）**——由**操作工**在每班/每日执行，检查设备基本状态（如气压、油位、异响、清洁度）。周期短、项目固定、单人即可完成。目的是「早发现」。
- **保养（计划性专业维护）**——由**维修技术员**按周/月/半年等周期执行，包含拆检、更换、润滑、测量等专业作业。周期长、项目多、需要备件与停机窗口。目的是「治根本」。

模面清理是介于两者之间的专项作业：频次高、动作单一、但需要**照片留证**。

### 2.2 组织与角色

| 角色 | 职责 | 系统中可执行的操作 |
|------|------|------|
| 操作工 / OPC | 执行点检、执行模面清理 | 提交点检结果、提交模面清理记录与照片 |
| 维修技术员 / Technician | 执行保养任务 | 开始保养、逐项完成任务、上传照片、提交报告 |
| 保养计划员 / Planner | 制定与调整保养计划 | 查询计划、确认计划、追加临时任务 |
| 主数据维护人 | 维护保养标准（机型↔任务清单↔频率） | 编辑主数据草稿、提交审核 |
| 主数据审核人 | 审批主数据变更 | 确认 / 取消确认主数据条目 |
| 班组长 / Team Leader | 三班转保养跟进 | 交接遗留问题、更新跟进状态 |
| 工序管理员 | 兜底管理 | 无直线上级时的通知兜底接收人 |
| 系统管理员 | 用户与权限维护 | 维护用户表、分配权限标志 |

> **现状说明**：EDS 中角色并非显式建模，而是通过 `userID` 表的多个权限列（如 `PM策略审核`、`PM提醒通知`、`PM班組确认邮件通知`、`任务安排权限`）逐项开关控制。Nexus 应将其整理为**显式的角色模型**（见 §4.1）。

### 2.3 成功标准

Nexus 上线后，满足以下条件视为替代成功：

1. §3 中列出的 8 项业务能力全部可用，且业务流程与现状一致（保真）
2. 历史数据完整迁移，可按保养编号 / 机台号 / 日期区间检索到迁移前记录
3. 附录 B 中列出的已知陷阱**不再出现**
4. 保养计划、点检、模面清理三类作业的周期计算与现状一致（不早不漏）
5. 通知邮件的收件人规则与现状一致（见 §4.2）

## 3. 业务能力需求

> **阅读约定**：每节按「业务目标 → 参与角色 → 业务流程 → 功能点 → 状态机 → 业务规则 → 验收标准」展开。字段级定义集中在附录 C。

### 3.1 保养主数据（PM Master Data）

#### 3.1.1 业务目标

定义「**哪个机型、按什么频率、执行哪份任务清单**」这一保养标准的唯一权威来源。所有保养计划的生成都以本表为依据。

#### 3.1.2 参与角色

主数据维护人（编辑）、主数据审核人（确认）。

#### 3.1.3 业务流程

```
维护人在「草稿区」编辑
        ↓
系统比对草稿与正式表的差异，列出变更项
        ↓
维护人提交变更
        ↓
审核人凭「工号 + 姓名 + 密码」验证审核权限
        ↓
确认 → 写入正式表 + 记录变更日志
（或）取消确认 → 回退
```

#### 3.1.4 功能点

| 编号 | 功能 | 说明 |
|:--:|------|------|
| MD-01 | 主数据列表 | 展示全部保养标准，支持按工序、机型筛选 |
| MD-02 | 行级编辑 | 可编辑频率、停机时间、策略、任务清单名、是否创工单等 |
| MD-03 | 变更差异比对 | 提交前列出「字段 / 原值 / 新值」三列对照 |
| MD-04 | 批量选择与确认 | 勾选多条记录，一次性确认或取消确认 |
| MD-05 | 审核权限校验 | 审核人须通过工号+姓名+密码三重校验，且具备审核标志 |
| MD-06 | 变更日志 | 每次确认/取消确认、每次字段修改均留痕（操作人、时间、字段、原值、新值） |
| MD-07 | 导入 | 支持从外部表批量导入；**正式表非空时禁止重复导入** |
| MD-08 | 行锁定 | 已确认的行不可直接编辑，需先取消确认 |

#### 3.1.5 字段说明（摘要，完整定义见附录 C.1）

| 字段 | 说明 | 取值示例 |
|------|------|------|
| 工序 | 适用工序 | `INJ` / `TF` / `PK` |
| Machine Type | 机型 | `6AX` |
| PM Frequency | 保养频率 | `半年` / `月` / `周` |
| 单次停机时间 / h | 该保养占用的停机工时 | `4` |
| PM Description | 保养描述 | 自由文本 |
| RBM 保养间隔时间 | 按运行时长触发的保养间隔 | 数值 |
| RBM 保养提醒间隔时间 | 提前提醒的时长 | 数值 |
| 强制保养频率 / Month | 按月强制的保养频率 | 数值 |
| 策略 / Strategy | 保养策略分类 | `预防性` / `预测性` / `基础性` |
| TasklistName | 关联的任务清单名称 | 对应任务清单表 |
| 是否创工单 | 该保养是否需要创建 SAP 工单 | 是 / 否 |
| 工单类型 | 创建工单时的类型 | 文本 |
| 是否计入 AEM | 是否纳入 AEM 统计 | 是 / 否 |
| 是否确认 | 审核状态 | `已确认` / `未确认` |
| 主数据 ID | 记录唯一标识（**审核与日志的定位键**） | 文本 |
| 确认人 / 确认时间 | 审核留痕 | `33017/范朝锋` / 时间戳 |
| 最后修改人 / 最后修改时间 | 编辑留痕 | — |

#### 3.1.6 业务规则

| 编号 | 规则 |
|:--:|------|
| BR-MD-1 | **主数据 ID 是唯一键**，审核、变更日志、取消确认均以它定位记录，不得以行号定位 |
| BR-MD-2 | 只有 `是否确认 = 未确认` 的行可被编辑 |
| BR-MD-3 | 取消确认时，`确认人`、`确认时间` 必须清空（不可残留） |
| BR-MD-4 | 审核权限来自用户表的独立标志位，与「是否有系统访问权」是两个维度 |
| BR-MD-5 | 导入是**全量替换**语义，正式表非空时必须拒绝执行 |
| BR-MD-6 | 变更日志**只增不改不删** |

#### 3.1.7 验收标准

- [ ] 未确认的行可编辑，已确认的行编辑入口不可用
- [ ] 提交变更时能看到逐字段的「原值 → 新值」对照
- [ ] 无审核权限的用户无法确认，报错信息明确指出是权限问题
- [ ] 确认后变更日志新增一条，含操作人、时间、字段名、原值、新值
- [ ] 取消确认后确认人与确认时间被清空
- [ ] 正式表非空时执行导入被拒绝，且正式表数据未被改动

### 3.2 保养计划（PM Plan）

#### 3.2.1 业务目标

让计划员与班组长能按**工序、车间、时间范围**查看「什么时候、哪台设备、要做哪些保养」，并识别超期项。

#### 3.2.2 参与角色

保养计划员、维修技术员、班组长。

#### 3.2.3 功能点

| 编号 | 功能 | 说明 |
|:--:|------|------|
| PL-01 | 多维度查询 | 按工序 + 车间 + 日期区间筛选 |
| PL-02 | 周视图 | 默认展示「前 20 周 ~ 后 4 周」的自然周区间（周日至周六） |
| PL-03 | 日期优先排序 | 表格排序规则为**今天最前 → 未来升序 → 过去降序** |
| PL-04 | 状态展示 | 显示每台设备的保养状态（见 §3.2.4） |
| PL-05 | 计划确认 | 计划员可对计划条目做确认 |

#### 3.2.4 状态定义

保养计划的状态共 **5 种**（已由业务方确认，见 OQ-8）：

| # | 状态 | 中文 | 判定条件 | 是否存储 | 展示色 |
|:--:|------|------|------|:--:|------|
| 1 | Not Started | 未开始 | 计划日期已到，但该设备在该日期**尚无保养记录** | ✗ 派生 | `#FFB6C1` |
| 2 | Assigned | 人员已分配 | 已为保养指派保养人员（`PM People` 非空），但尚未开始 | ✓ 存储 | `#00BFFF` |
| 3 | Temp Task Added | 已添加临时任务 | 已追加计划外任务（`TEM-00`），但尚未开始 | ✓ 存储 | `#9370DB` |
| 4 | Ongoing | 进行中 | 已点击「开始保养」，尚未提交 | ✓ 存储 | `#FFC300` |
| 5 | Finished | 已完成 | 保养已提交完成 | ✓ 存储 | `#32CD32` |

**状态流转**：

```
未开始 ──[指派保养人员]──> 人员已分配 ──┐
   │                                    │
   └──[追加临时任务]──> 已添加临时任务 ──┤
                                        ├──[开始保养]──> 进行中 ──[提交]──> 已完成
                                        ┘
```

**排序权重**（用于列表排序，越大越靠后）：未开始 `0` < 人员已分配 / 已添加临时任务 / 进行中 `1` < 已完成 `2`

> **「未开始」是派生状态**：系统中并不存在「未开始」的记录，而是当某设备在某计划日期查不到保养记录时，由查询逻辑补一个「未开始」。Nexus 实现时需注意这一语义——**不要为未开始的计划创建空记录**。

> ⚠️ **现状问题（严重）**：EDS 中「已完成」存在 **四种**写法并存——`已完成`、`Finished`、`Done`、`Completed`；状态判定全部依赖「字符串是否包含某关键词」的包含匹配。新增任一状态都可能因关键词重叠而误判。Nexus **必须**改为**规范化的状态枚举 + 显式状态 ID**（见附录 B-1、B-9）。

#### 3.2.5 业务规则

| 编号 | 规则 |
|:--:|------|
| BR-PL-1 | 计划日期来源于主数据的频率推算，同一机台同一任务清单不得重复生成同期计划 |
| BR-PL-2 | 日期区间的两端均**含当日**（闭区间） |
| BR-PL-3 | 周视图的「周」为**周日至周六**，不是 ISO 周一至周日 |
| BR-PL-4 | 查询结果必须可导出/可被外部 BI 读取（现状由 Domo 消费，见 §1.2.2） |

#### 3.2.6 验收标准

- [ ] 按工序+车间筛选后，只出现该组合下的计划
- [ ] 日期区间边界日的记录被正确包含
- [ ] 周视图覆盖前 20 周至后 4 周，边界周完整
- [ ] 今天的记录排在首位，未来按时间升序，过去按时间降序
- [ ] 状态显示与实际业务状态一致，无「已完成 / Done」这类混合写法

### 3.3 保养任务管理（PM Task）

#### 3.3.1 业务目标

维修技术员按任务清单逐项执行保养，记录每项的结果与测量值；验证人复核完成质量。

#### 3.3.2 参与角色

维修技术员（执行）、验证人（复核）、保养计划员（追加临时任务）。

#### 3.3.3 业务流程

```
计划生成保养记录（含 PM No.）
        ↓
技术员点击「开始保养」
   → 记录开始日期、开始时间，状态置「进行中」
        ↓
逐项执行任务清单
   → 每项可标记完成 / 未完成，可填测量值、备注、上传图片
        ↓
提交 → 记录结束日期、结束时间，状态置「已完成」或「待确认」
        ↓
验证人对任务逐项复核 → 记录验证结果
        ↓
生产确认 → 生成 PDF 报告（见 §3.4）
```

#### 3.3.4 功能点

| 编号 | 功能 | 说明 |
|:--:|------|------|
| TK-01 | 开始保养 | 记录开始时间，状态转「进行中」 |
| TK-02 | 任务清单渲染 | 按任务清单逐项展示：任务号、分区、功能、故障模式、任务描述、频率、策略、所需资源、技能等级、工具、预计工时 |
| TK-03 | 逐项完成 | 每项标记完成/未完成 |
| TK-04 | 数值记录 | PdM（预测性）类任务需录入测量值，含上下限判定 |
| TK-05 | 备注与图片 | 每项可填备注、上传照片 |
| TK-06 | 临时任务 | 追加计划外任务（任务号 `TEM-00`），记录临时原因 |
| TK-07 | 未完成项统计 | 自动汇总未完成任务数与明细 |
| TK-08 | 任务验证 | 验证人对每项录入：验证结果、失败原因、验证人工号/姓名、验证时间 |
| TK-09 | 留样管理 | 记录留样问题、留样图片、留样工号 |
| TK-10 | 班组交接 | 记录跨班次交接信息 |

#### 3.3.5 状态机

状态定义见 §3.2.4（共 5 态）。任务执行视角的流转如下：

```
未开始（派生：无记录）
   │
   ├──[指派保养人员]──> 人员已分配 ──┐
   │                                 │
   └──[追加临时任务]──> 已添加临时任务 ┤   ← 追加任务后任务数 +1
                                     │
                              [开始保养]
                                     ▼
                                  进行中
                                     │
                                  [提交]
                                     ▼
                                  已完成
                                     │
                          [任务验证]（独立于状态，单独记录）
```

> **关键语义**：
> - **「人员已分配」与「已添加临时任务」都是"可开始但未开始"的状态**，两者都允许点击「开始保养」。
> - **任务验证不改变保养状态**，验证结果独立存储（见 BR-TK-6）。因此状态流转是单向的，验证是旁挂的记录维度。
> - 状态一旦进入「已完成」即为终态，不可回退（如需修正，应通过撤销并重建记录，而非改状态）。

#### 3.3.6 业务规则

| 编号 | 规则 |
|:--:|------|
| BR-TK-1 | **PM No. 是保养记录的唯一业务编号**，格式为「日期 + 机台号」，如 `20260105H1FCS005` |
| BR-TK-2 | 任务明细以结构化数据存储，**每项含 30+ 个属性**（见附录 C.2），不是纯文本 |
| BR-TK-3 | 「总任务数量」「未完成数量」「备注数量」由明细自动汇总，不得手工填写 |
| BR-TK-4 | PdM 类任务录入数值时，须按 `LL Limited` / `HH Limited` 做越限判定 |
| BR-TK-5 | 临时任务不占用标准任务号，统一使用 `TEM-00` 前缀 |
| BR-TK-6 | 验证记录**独立存储**（不覆盖任务明细），保留完整验证历史 |
| BR-TK-7 | 保养记录与工序、车间强绑定；**跨工序/车间查询必须显式筛选**（见附录 B-2） |

#### 3.3.7 验收标准

- [ ] 开始保养后，开始日期与开始时间被正确记录
- [ ] 任务清单按标准模板完整渲染，无遗漏项

### 3.7 点检（Inspection）

#### 3.7.1 业务目标

操作工每班/每日对设备做自主点检，及时发现异常并上报。点检的**核心约束是周期性与不重复**：同一台设备在同一个周期内不应被重复点检，也不应被遗漏。

#### 3.7.2 参与角色

操作工（OPC）、维修技术员、班组长。

#### 3.7.3 业务流程

```
选择「车间 + 工序」
        ↓
选择点检人类型（操作员 / 技术员）
        ↓
选择机型 → 选择机台号
        ↓
系统按机台带出任务清单，并按频次过滤
   · 仅取「生效 / Effective」状态的任务
   · 频次由任务清单自身决定，不由用户选择
        ↓
逐项点检：正常 / 异常
   · 异常项需填写说明、可上传照片
        ↓
提交 → 生成点检记录（编号 = 年 + 周）
```

#### 3.7.4 关键机制：周期性去重

这是点检模块**最重要也最容易实现错**的机制：

| 机制 | 说明 |
|------|------|
| 周期标识 | 以「年 + 周」（YearWeek，格式如 `2026W02`）标识某一周 |
| 去重维度 | **机台号 + 任务类型**的组合，在**同一周内**只允许点检一次 |
| 实现要求 | 已在本周点检过的「机台号 + 任务类型」组合，**不得再出现在待点检清单中** |
| 跨周期重置 | 进入新的一周后，上一周的记录不再影响本周可点检范围 |
| 运行时长触发 | 除周期触发外，另有一套基于设备**运行时长**触发的点检规则（独立数据源） |

#### 3.7.5 点检记录字段（摘要，完整定义见附录 C.4）

| 字段 | 说明 |
|------|------|
| Code | 点检编号（年 + 周） |
| Workshop / Process | 车间 / 工序 |
| MachineType / Workcenter | 机型 / 机台号 |
| Frequency | 点检频次（来自任务清单） |
| PointChecker | 点检人 |
| Ownner | 责任人 |
| Submit Date | 提交日期 |
| Team | 班次 |
| 点检任务明细 | 结构化明细（JSON） |
| 点检任务数量 | 明细条数汇总 |
| 异常已解决明细 / 数量 | 异常项中已解决的 |
| 异常未解决明细 / 数量 | 异常项中未解决的 |
| 异常备注明细 / 备注数量 | 备注汇总 |

#### 3.7.6 业务规则

| 编号 | 规则 |
|:--:|------|
| BR-IN-1 | 任务清单只取 `Status = 生效 / Effective` 的条目，其余（如停用）不参与点检 |
| BR-IN-2 | 点检频次由任务清单的 `Frequency` 字段决定，**前端不可由用户随意更改** |
| BR-IN-3 | 同一周内「机台号 + 任务类型」不得重复点检（见 §3.7.4） |
| BR-IN-4 | 「点检任务数量」与各项异常数量由明细**自动汇总**，不得手工填写 |
| BR-IN-5 | 异常项必须区分为「已解决」与「未解决」两类，分别记录 |
| BR-IN-6 | 点检任务清单按 `Unit / Parts / Inspection Std / Tool / Method` 描述检查标准，Nexus 需完整保留这些字段 |
| BR-IN-7 | 班次取值为 A班 / B班 / C班 / D班。其中 **A/B/C 三班按时间区间自动判定**（00:00–08:00 / 08:00–16:00 / 16:00–24:00）；**D班 为常白班（长白班）**，适用于不参与三班倒的技术员/常日班人员（业务方已确认，见 OQ-7） |

#### 3.7.7 验收标准

- [ ] 本周已点检的「机台号 + 任务类型」组合不再出现在待点检清单
- [ ] 跨周后，上一周的记录不再阻止本周点检
- [ ] 未标记 `生效` 的任务不出现在点检清单中
- [ ] 点检频次与任务清单定义一致，且用户无法篡改
- [ ] 异常项被正确分为「已解决 / 未解决」并分别计数
- [ ] 提交后的记录可按周次、工序、机台号检索

### 3.8 模面清理（Mold Surface Clean）

#### 3.8.1 业务目标

按计划对模具表面执行清洁作业，并通过**拍照留证**确保作业真实执行。对未生产（设备未开机）的情况单独记录，避免污染统计。

#### 3.8.2 参与角色

维修技术员、操作工。

#### 3.8.3 业务流程

```
系统展示模面清洁计划列表
   · 每行 = 一个「序列号 + 工序 + 机台号 + 计划日期」
   · 排序：今天最前 → 未来升序 → 过去降序
        ↓
点击「跟进」
        ↓
确认开始清洁
        ↓
输入技术员工号
        ↓
分支判断设备状态：
   ├─ 已开机并拍照 → 拍照 → 提交（记录照片链接）
   └─ 记录为未生产 → 提交（记录「未生产」标记）
        ↓
列表刷新，该行状态更新
```

#### 3.8.4 状态机

| 状态 | 中文 | 含义 | 来源 |
|------|------|------|------|
| No Start | 未完成 | 尚未执行 | 无记录（默认） |
| Done | 已完成 | 已清洁并拍照留证 | 有记录，且含照片 |
| Unproduced | 未生产 | 设备未开机，无法执行 | 有记录，标记为未生产 |

#### 3.8.5 数据记录结构

每条记录含字段：序列号、工序、机台号、计划日期、技术员工号、执行日期、**照片链接或「未生产」标记**。

> ⚠️ **现状问题**：EDS 把「照片链接」和「未生产」标记**塞进同一列**，状态靠该列内容的类型（是 URL 还是文本）反推。Nexus **必须**改为**独立的状态字段 + 独立的照片字段**（见附录 B-3）。

#### 3.8.6 业务规则

| 编号 | 规则 |
|:--:|------|
| BR-MC-1 | 计划列表**展示全部日期**，不过滤；排序为今天最前、未来升序、过去降序 |
| BR-MC-2 | 技术员工号在**两种流程下都是必填**（含「未生产」） |
| BR-MC-3 | 选择「已开机并拍照」时，**照片为必填**，未拍照不得提交 |
| BR-MC-4 | 照片需持久存储并可随时预览，不得依赖客户端临时数据 |
| BR-MC-5 | 状态必须为**独立字段**，不得由其他列的内容反推 |
| BR-MC-6 | 同一「序列号」的**重复提交必须被阻止**（业务方已确认，见 OQ-4）。需要修正时应走显式的「修改」流程并留痕，而非允许重复提交后覆盖 |

#### 3.8.7 验收标准

- [ ] 计划列表按「今天 → 未来 → 过去」排序
- [ ] 未输入工号无法提交（两种流程均如此）
- [ ] 选「已开机并拍照」但未拍照时，提交被阻止并提示
- [ ] 提交后照片可在列表中预览
- [ ] 「未生产」记录不产生照片字段，且状态明确
- [ ] 三种状态在界面上有清晰可辨的视觉区分

## 4. 跨切面需求

以下需求为 §3 中多个业务能力共用，**必须统一实现**，不得逐模块各写一套。

### 4.1 身份认证与权限

#### 4.1.1 现状

EDS 的用户与权限集中在用户表（`userID`）中，共 **65 列**，按「人」逐列打勾授权。关键列包括：

| 列 | 用途 |
|------|------|
| SAPID / NAME / PWD | 身份三元组，登录与审核校验都用它 |
| 车间 / 工序 | 用户所属范围，决定其默认看到的数据 |
| ROLE / Access | 基础访问权限 |
| PM策略审核 | 是否可审核保养主数据 |
| PM提醒通知 / PM班組确认邮件通知 | 是否接收对应通知 |
| 直线上级邮箱 / Supervisor Email | 通知抄送对象 |
| 任务安排权限、留言板权限、故障报告管理权限… | 各模块独立开关 |

#### 4.1.2 需求

| 编号 | 需求 |
|:--:|------|
| AU-1 | Nexus **必须**建立**显式角色模型**，将现状中 65 个散列权限标志归纳为角色 + 权限点的组合，而不是继续按列打勾 |
| AU-2 | 权限判定**必须**基于权限点，不得基于用户姓名、工号等身份属性做隐式判断 |
| AU-3 | 用户可归属多个工序/车间，其数据可见范围由归属决定 |
| AU-4 | **密码必须以加盐哈希存储，禁止明文**（见附录 B-4） |
| AU-5 | 审核类操作（如主数据确认）**必须**在服务端再次校验权限，不得仅依赖前端隐藏按钮 |
| AU-6 | 登录态**必须**由服务端会话或令牌承载，不得依赖浏览器 `sessionStorage` 中的明文身份 |

> **AU-6 说明**：EDS 现状是把用户身份（含密码）存在浏览器 `sessionStorage` 并随 URL 参数在页面间传递。这在 Nexus 中不可接受。

### 4.2 通知与提醒

#### 4.2.1 现状

EDS 的通知规则集中在《通知邮件 通用需求模板》中，涉及 FailureReport、Inspection、PM_Task 等模块。核心规范如下：

| 维度 | 规范 |
|------|------|
| 语言 | 邮件标题、正文所有字段标签**中英双语** |
| 发送方式 | 多收件人**合并为一封**：`to` 为第一收件人，其余填 `cc` |
| 收件人规则 | **操作方通知被操作方，操作方自己抄送**（例：验证人操作 → `to`: 责任人，`cc`: 验证人） |
| 汇总类 | 按接收人邮箱分组，**每人一封**，含其名下所有待处理记录 |
| 邮箱提取 | 从 `名字【邮箱】` 格式中提取 |
| 样式 | HTML 富文本；表头底色 `#E60012`、白字；数据行交替条纹（`#f5f5f5` / `#ffffff`）；容器圆角 8px + 阴影 |

## 6. 上线与切换策略

> **本节状态：待决策。** 以下是三条可选路径及其前置条件与风险，供后续决策使用。Nexus 团队需在方案确定后补充对应的实施细节。

### 6.1 方案甲：试点先行，逐步推广

**做法**：选择单一工序或车间试点运行 Nexus，跑通后再逐个推广，直至覆盖全部工序车间。试点期间 EDS 与 Nexus 并存。

| 维度 | 说明 |
|------|------|
| 前置条件 | 试点范围的数据可独立切分；两套系统的数据不互相污染 |
| 优点 | 风险最低；问题在局部暴露，可快速回退 |
| 风险 | 并存期数据可能双写/不一致；一线人员需同时使用两套系统，易混淆 |
| 需补充 | 试点范围定义、并存期的数据归属规则、推广的准入条件 |

### 6.2 方案乙：并行运行，对账后切换

**做法**：新老系统同时运行一段时间，同一笔业务在两套系统中各记一次，定期对账，验证一致后停用 EDS。

| 维度 | 说明 |
|------|------|
| 前置条件 | 有明确的对账口径（以哪个字段为基准）；一线人员愿意承担双份录入工作量 |
| 优点 | 数据正确性有实证；切换决策有依据 |
| 风险 | 双份录入负担重，执行走样会使对账失去意义；并行周期可能被无限拉长 |
| 需补充 | 对账维度与容差、并行期时长、退出条件 |

### 6.3 方案丙：一次性切换

**做法**：停用 EDS，一次性迁移全部历史数据，Nexus 直接上线。

| 维度 | 说明 |
|------|------|
| 前置条件 | 迁移方案经过完整演练并验证；有明确回滚预案与回滚窗口 |
| 优点 | 无并存期，无数据双写问题；一次性完成 |
| 风险 | 无并行验证，问题在生产环境暴露；回滚成本高 |
| 需补充 | 切换窗口（建议非生产时段）、回滚触发条件、回滚演练结果 |

### 6.4 无论选哪条路径都必须具备的

| 编号 | 要求 |
|:--:|------|
| SW-1 | 切换前完成一次**全量迁移演练**，并出具校验报告 |
| SW-2 | 保留 EDS 的**只读访问能力**，直至新系统稳定运行满一个完整保养周期 |
| SW-3 | 明确**回滚触发条件**与决策人 |
| SW-4 | 一线人员的操作培训与过渡期支持方案 |

## 附录 B：现状痛点 → 改进要求

本附录列出 EDS 中已识别的设计缺陷与风险。**这些问题的共同点是：外部团队无法从需求描述中发现它们，但重建时极易重蹈覆辙。** 每一条都是对 Nexus 的**强制要求**。

| # | 现状问题 | 证据 | 对 Nexus 的要求 |
|:--:|------|------|------|
| B-1 | **状态值不统一**：同一个「已完成」在代码与历史数据中存在 **4 种写法**（`已完成`、`Finished`、`Done`、`Completed`）；且状态判定全靠「字符串是否包含某关键词」的包含匹配 | 代码中 4 种字面量并存；徽章渲染与行配色均用 `includes('已完成')` 之类判断；「进行中」同样存在中英双写法 | 使用**规范化状态枚举 + 显式状态 ID**，全系统单一取值来源；界面配色与业务判断**禁止**依赖字符串包含（见 §3.2.4） |
| B-2 | **工序/车间硬编码 + 分表陷阱**：数据曾按「工序 × 车间」拆成 6 张物理分表（INJ/TF/PK × TB1/TB2），新增设备类型需手工建表；代码中多处硬编码分表名数组 | 见《需求文档_PM分表合并》 | 工序/车间作为**数据字段**而非物理分表；新增工序/车间**零代码改动** |
| B-3 | **模面清理状态混列**：「照片链接」与「未生产」标记塞进同一列，状态靠内容类型（URL 还是文本）反推 | 写入逻辑中同一列位置存 URL 或字符串「未生产」 | 状态为**独立字段**；照片为**独立字段**；两者不得互相推断 |
| B-4 | **密码明文存储**：用户表中 `PWD`、`PWD_back`、`last_PWD` 均以明文保存 | 用户表列定义 | 密码**加盐哈希**存储；禁止保留历史明文密码字段；登录校验不得明文比对 |
| B-5 | **附件公开链接**：保养报告 PDF 使用 `?usp=drivesdk` 形式的公开链接 | 保养记录报告字段样例 | 附件访问**受权限约束**，使用带时效的授权链接，而非公开链接 |
| B-6 | **并发写入无保障**：多个用户同时写入同一表格区域时无锁机制，后写覆盖先写 | 表格直写模式 | 明确**并发控制策略**（乐观锁 / 版本号 / 事务），冲突时给出提示而非静默覆盖 |
| B-7 | **日期类型退化**：表格读取返回的是日期对象，直接传给前端会静默失败或时区偏移 | 数据层特性 | 日期在**存储、传输、展示**三环节类型一致；API 层统一为 ISO 8601 字符串 |
| B-8 | **靠列位置定位数据**：大量代码以 `第 N 列` 而非字段名引用数据，插入新列即导致全线错位 | 代码中大量列号引用 | 数据结构以**字段名**寻址；列顺序变化不得影响业务逻辑 |
| B-9 | **身份走前端存储**：用户身份（含密码）存于浏览器 `sessionStorage`，并经 URL 参数在页面间传递 | 前端 `sessionStorage` 用法 | 身份由**服务端会话/令牌**承载；不得在 URL 或客户端存储中出现凭据 |
| B-10 | **执行时长上限**：单次后端调用有 6 分钟上限，大表读写易整体失败 | 运行平台特性 | 批量操作**分批 + 断点续传**；单次操作不因数据量增长而整体失败 |
| B-11 | **数据源碎片化**：仅点检一个模块就横跨 5 个独立数据表；保养横跨 3 个 | 各模块数据源清单 | 统一数据模型；模块间通过**明确定义的接口**交互，而非各自读对方的原始表 |
| B-12 | **工号无校验**：模面清理中技术员工号为**手工输入**，不校验其是否存在或有效 | 提交逻辑仅校验非空 | 人员选择**从用户主数据中选择**，而非自由输入；服务端校验有效性 |
| B-13 | **时区混用**：系统内 `Asia/Hong_Kong` 与 `Asia/Shanghai` 并存 | 代码中两种时区字面量 | 全系统**统一时区**并显式声明 |
